# 01 · 競賽規則與繳交

> 來源：《競賽須知 115.08.27 版》原文（`source/競賽須知_115.08.27.txt`）＋入門指引。標 **[規則]** 為硬性規定，標 **[建議]** 為主辦建議。

## 基本資訊
- 主辦：臺北市政府資訊局；承辦：台北市電腦商業同業公會（規則問題問承辦，技術問題開 TownPass GitHub issue）
- 比賽：**115/11/7（六）～11/8（日），中間不間斷**，臺北市立大學天母校區體育館。題目當天正式公布。
- 隊伍 **4～5 人**，需有主要、次要聯絡人。**全員實體到場報到**，報到截止後 30 分鐘未到可取消資格；工作坊與比賽當天都會查驗政府核發證件。
- 建議技能：Git、Docker、Postman；HTML/CSS/JS/Vue；**Spring Framework、Hibernate、Tomcat**；Flutter/Dart；市政知識。
- 建議角色：專案規劃師、資料工程師、前端工程師、後端工程師。
- 主要目標：**以台北通為基礎，開發城市通微服務新功能**。
- 不得抄襲、仿冒或侵權。電腦設備自備。

## 評分標準 [規則]（序位制：各評審評分轉成序位後加總）
| 階段 | 項目 | 說明 | 配分 |
|---|---|---|---|
| **初選（約 2 分鐘）** | 服務應用 | 想法創意，且與題目相符 | **40** |
| | 視覺呈現 | 服務功能介面清楚美觀 | 30 |
| | 技術完整度 | 架構清楚、資料來源正確、功能運行流暢 | 30 |
| **決選（約 5 分鐘＋問答）** | 服務應用 | 情境完整且實用 | 25 |
| | 服務完整度 | **服務落地的可能性與難易度** | **30** |
| | 技術穩定度 | 操作流暢度與系統穩定性 | 20 |
| | 視覺呈現 | 操作介面與功能完整度 | 15 |
| | 創意及公益性 | 活用開源技術、符合公共利益、作品創意、發表完整順暢 | 10 |

→ 初選：**切題＋創意**最重要，UI 也佔 30 分。決選：**能不能真的上線**最重要，其次是穩定度。
→ **每一項要靠什麼實作拿分** → [12-scoring-playbook.md](12-scoring-playbook.md)（含選手須知手冊新增的上傳截止、輪桌方式、決選時間）。

## 獎金與得獎義務
- 第一名 30 萬、第二名 15 萬、第三名 10 萬、佳作 3 隊各 5 萬（以隊伍為單位，依法扣繳）。
- 比賽結束後 **2 週內**主辦會 email 通知；接到通知隔天起 **1 個月內**要把指定元素整併進官方程式庫，**完成整併後才發獎金**。
- 整併時若發現**使用第三方商用服務**或沒配合上傳／修改，可撤銷獎項或獎金。
- 得獎者在之後的黑客松要回來分享經驗。
- 獎金分配：得獎隊伍在指定期間內**自己決定分配方式**，書面提供分配方式與各人匯款帳號（本國銀行）；整併完成後 30 日內匯款。逾期沒交 → 主辦平均分配、暫保留或依法處理。各人依所得稅法扣繳。→ **賽前隊內先講好怎麼分**。
- 若主辦認定作品整併有困難或不適合整併，獎金不以整併為條件。
- 整併範圍只限比賽期間完成的作品，只會要求簡易修改或刪減，不會要求開發新功能；有困難可提出調整。

## 授權與開源 [規則]
- 比賽期間作品放在**公開 repo**，附**主辦指定的授權聲明**；授權 **AGPL-3.0**。
- 得獎公布後 repo **保持公開至少一年**；得獎隊伍需協助整併（2 週內 email 通知，1 個月內完成，以小幅修改為主）。
- AGPL 要點：任何人可用/改/散布；改版須同授權開源；**透過網路提供服務也要提供原始碼**。
- 套件選擇：MIT / BSD / Apache-2.0 可納入；「僅供個人使用」「不得再散布」者不要用。TownPass 本身 GPL-3.0。
- 選開源、免費的模組（數位自主權）。
- 須知原文：只能用開源軟體或套件，限制使用**可能產生授權費、訂閱費、付費功能，或影響上架的商用模組**（例如 Google Maps）。違反者得扣分或取消資格。
- 授權期間：自公布得獎結果日起 **1 年內不得下架**。
- **LICENSE 必須載明的 AGPL 聲明（須知 捌-一-(二)，照抄後填入角括號）**：

## 程式碼的時間範圍 [規則推論]
- 須知寫「整併範圍限得獎隊伍於**競賽期間完成的作品**」、「不得抄襲」。
- → 賽前只準備**與題目無關的骨架**（bridge、Dockerfile、部署設定、測試頁），題目相關的功能一律當天寫。賽前準備的骨架在 README 註明。

## 地圖 [規則]
- 必須用開源方案：**Leaflet、MapLibre** + **OpenStreetMap** 或**國土測繪中心**圖資。
- 不可：Google Maps（含 `google_maps_flutter`、`vue3-google-map`）、Mapbox。

## AI [規則]
- 開發階段可用雲端 AI（企劃、寫程式、除錯、整理資料）。
- **執行時 LLM 推論必須在裝置端**，包含使用者輸入與作品資料的推論；不得用雲端 API 或遠端模型。
- 開發階段還可以用雲端 AI 做**模型訓練、微調、量化、轉換**。
- 允許：一般後端（登入、DB、檔案、排行榜、同步），但**不得把使用者輸入或作品資料送到後端做 LLM 推論**；**預先生成**的固定文字/圖片/程式碼可以用，但**不得宣稱是執行時的即時 AI 功能**。
- 評審可要求**關閉 Wi-Fi 與行動網路**，用現場給的全新題目驗證。
- 禁用危害國家資通安全清單所列 AI 工具與模型（含大陸廠牌）。
- 評審可能**關網路現場出題**驗證 LLM。
- README 揭露：**模型名稱、版本、量化格式、推論框架、來源**。

## 資料 [規則]
- 核心資料須為**合法開放資料並註明出處**；非核心可用模擬資料。
- README 與 Demo 標示資料集名稱與連結。

## 部署 [規則/建議]
- 部署平台不限，請用**免費方案**；網頁須 **HTTPS**。
- 「可移轉、可維運、可上架」→ 資訊局拿到 repo 能順利跑 → 準備 **Dockerfile**。

## 發表 [規則]
- **作品須於 11/8 09:00 前上傳主辦作品系統**（選手須知手冊 p5；帳密見行前須知／賽場須知）。
- 初選 10:00–13:30：評審**輪桌到座位**，每次發表 2 分鐘＋Q&A 1 分鐘；A、B 兩組評審各評一次 → 會評兩次。
- 決選 14:10–16:40：15 隊，**每隊 10 分鐘＝5 分鐘發表＋5 分鐘 Q&A**，順序抽籤；自帶 Demo 筆電，控台只有 HDMI 線。
- **投影實際運作畫面，不使用任何形式簡報（PPT、Canva 等）**。各隊須上台發表才可參加評選。
- 主辦建議內容：題目 → 創意來源與應用場景 → 開發項目、資料來源與技術細節 → 實際運作展示。

## 評估六面向（決選問答常圍繞這些）
| 政府端（數位治理） | 市民端（民眾需求） |
|---|---|
| **安全**：個資保護、防攻擊、能被監督 | **參與**：方便表達意見、參與社區、民主自決 |
| **創新**：新想法、鼓勵創造、能持續改 | **便利**：數位歸戶、無縫接軌、主動推薦 |
| **有感**：民眾有感、解決需求、可擴充 | **透明**：用語淺白、即時更新、指引清楚 |

→ README 與答辯每一項準備一兩句。另需思考**營運接手**：資料誰更新、問題誰處理（資訊局營運團隊會維護）。

## 城市通的使用者類型（講義 p39，決選「服務完整度＝落地可能性」會問）
| 層 | 類型 | 說明 |
|---|---|---|
| 民眾層 | 核心用戶 | 經常用台北通，涵蓋政府服務與社區活動 |
| | 潛在用戶 | 有需求，但還沒用台北通 |
| | 周邊使用者 | 只用其中幾個功能 |
| 營運層（資訊局） | 營運管理團隊 | 日常營運、技術支援、用戶服務；**作品上線後由他們維護** |
| | 其他機關 | 想把自己的系統或政策接進來 |
| | 商家與潛在商家 | 在平台上經營，或有意加入的商家 |

微服務六種常見型態（講義 p37，可組合）：公告・優惠・查詢・申請・支付・地圖。好作品要同時兼顧「民眾需求」與「數位治理（提升政府效率、透明）」。

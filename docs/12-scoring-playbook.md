## 1. 選題時就決定分數的項目（brainstorm 用）
| 評分項目 | 配分 | 選題時要確認 |
|---|---|---|
| 初選・服務應用「想法創意且與題目相符」 | **40** | 能用一句話說「**哪一種市民**，在**什麼情境**，用這個服務解決**什麼問題**」，而且直接對應官方題目的關鍵字。和現有台北通功能或往屆作品（[08](08-past-winners.md)）不重複 |
| 決選・服務完整度「服務落地可能性及難易度」 | **30** | 核心資料是**真的開放資料、會持續更新**；不需要市府沒有的資料或新法規；整併只要放進 TownPass 的 WebView、改幾個 App 檔案 |
| 決選・創意及公益性「符合公共利益」 | 10 | 服務的是一般市民或弱勢族群，不是商業用途；可以對應 01 的六面向（安全、創新、有感、參與、便利、透明）|

> 選題否決條件：主流程需要雲端 LLM、需要 Google 地圖、核心資料只能用假的、1 天做不出一條完整主流程。

## 2. 初選（100 分，2 分鐘＋1 分鐘 Q&A，評兩次）
| 項目 | 配分 | 評審看什麼 | 我們的實作 | 負責 |
|---|---|---|---|---|
| **服務應用** | **40** | 想法有創意、與題目相符 | 首頁第一屏就看得出這個服務是做什麼的（標題＋一句說明）；主流程對應題目情境；有一個**「哇」的點**（例如用到 App 能力：定位找最近的、推播提醒、掃碼） | 規劃＋前端 |
| **視覺呈現** | 30 | 服務功能介面清楚美觀 | 照 **Town Pass UI Kit**（Figma）的顏色、字級、圓角，看起來像台北通原生功能；手機版面（375px 寬）不破版、字不會太小；地圖標記、圖示一致；載入中、空資料、錯誤都有畫面，不是白屏 | 前端 |
| **技術完整度** | 30 | 架構清楚、資料來源正確、功能運行流暢 | ① 架構清楚：web／api／App 分層，README 有架構圖 ② **資料來源正確**：畫面上顯示資料出處與更新時間（例如「資料來源：臺北市資料大平台，更新於 11/8 08:00」）③ 流暢：後端快取開放資料，回應時間 < 1 秒；Cloud Run 先暖機 | 後端＋前端 |

**初選 Demo 要求**：3 分鐘內要能**完整重做一遍**，而且至少重複 2 次（A、B 組）＋臨時被問。所以要有「重置」方法，例如清除 localStorage 的按鈕或重新開服務；不要依賴當下才產生的資料。

## 4. 不能用簡報 → 「說明」要做進作品裡
不能放 PPT，但主辦要我們講理念、架構、資料來源。做法：
- 在微服務裡做一個「**關於這個服務**」頁（或 README 頁面），放：一句話理念、目標使用者、**資料來源清單（含連結）**、架構圖、使用的開源技術。這是作品的一部分，同時也符合「資料要註明出處」和「透明」面向。
- 架構圖放在 GitHub README，Demo 時可以切到瀏覽器開 repo 頁面說明（這是展示作品，不是簡報）。
- 不要做成整頁投影片式的頁面，以免被認為是變相簡報。
